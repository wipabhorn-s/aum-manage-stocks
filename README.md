# Aum Manage Stocks

A back-office stock management platform for small retail shops. One owner manages
several branches from a single central product catalog, gives staff per-shop
permissions, sells through a barcode POS, and adjusts stock by typing plain Thai
into a chatbot on the web or on LINE.

Built as a pnpm monorepo: a **NestJS** REST API and a **Next.js (App Router)** web client.

**Live demo:** https://aum-manage-stock.vercel.app

## Features

### Shop owner
- **Central product catalog**: create a product once and list it in any of your
  shops. Each shop keeps its own sell price, stock quantity and low-stock threshold
- **Multi-shop management**: create, edit, pause/resume and delete shops, and pin
  each shop's location on a map (Leaflet + OpenStreetMap)
- **Stock in / adjust / transfer** between shops, with lot-based cost tracking
  (oldest lot is used first) and a full stock history per shop
- **POS**: build a cart by picking products (every plan) or by scanning barcodes
  through the camera (QR + EAN-13, Plus / Pro), then void a sale with a reason
  if needed. Stock is cut automatically and each bill keeps the price and cost
  at the time of sale
- **Dashboard**: every plan gets the per-shop sales summary. Plus / Pro add best
  sellers, dead stock, sales trend, sales by category and a view across all shops
- **Staff management**: invite staff, assign them to one or more shops, and grant
  per-shop permissions
- **Subscription billing**: upgrade or renew a plan and pay by card on our own page
  (Stripe Payment Element). Upgrades charge only the difference, and unpaid
  invoices expire after a day
- **In-app notifications**: low stock, plan expiring in 7 days, and shop or
  product quota reached
- Thai / English interface

### Chatbot stock adjustment (Plus / Pro)
- Type a message such as `เพิ่มโค้ก10` ("add 10 Coke") on the web or in LINE
- Four kinds of command: add stock, reduce stock, sell, and transfer to another shop
- An LLM (Ollama) parses it and the result is validated with Zod. When the LLM is
  not configured or fails, a rule-based parser handles the standard phrasings
- If a product name matches several products, the bot asks which one. An owner
  with several shops is asked which shop first when using LINE
- The parsed result is saved as a **pending action**, shown back for review, and
  only written to the stock ledger after the user confirms. Pending actions expire
  if nobody confirms them, so a reply can arrive later through a LINE webhook
- A LINE user can only use the bot while their account is linked to LINE
- Staff need the per-shop chatbot permission, and the owner's plan must include it

### AI recommendations (Pro)
- Restock, clearance and promotion suggestions per shop, generated by an LLM when
  the user asks for new ones, and cached in the database
- New suggestions are pushed to everyone viewing that shop over Socket.io, so the
  LLM is never called while a page renders. Users can dismiss a suggestion

### Admin
- Platform overview: users by role, shops, suspended accounts, products, and
  subscribers per plan
- Search and filter users and shops, and suspend / reactivate either one with a
  reason. Admins can't suspend themselves or other admins, and nobody can suspend
  a super admin
- Super admins can create admin accounts, suspend admins and change admin roles
- Every admin action is written to an audit log

### Auth and account security
- Register with email + password and **email verification**
- Sign in with **Google** or **LINE**, and link or unlink either one from the profile
- Forgot / reset password, and change the account email (current password + a link
  sent to the new address)
- Optional **two-factor authentication** (TOTP authenticator app) with recovery
  codes. When it is on, it is required on **every** login channel: password,
  Google and LINE
- Roles: `SUPER_ADMIN`, `ADMIN`, `SHOP_OWNER`, `SHOP_STAFF`

## Subscription plans

Quota only changes by upgrading the plan. There are no add-on purchases.

| Plan | Price / year | Shops | Active products | Staff | Chatbot | Barcode POS | AI recommendations |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Free | ฿0 | 1 | 100 | 0 | ✗ | ✗ | ✗ |
| Plus | ฿2,499 | 3 | 3,000 | 6 | ✓ | ✓ | ✗ |
| Pro | ฿3,499 | 5 | 5,000 | 10 | ✓ | ✓ | ✓ |

- Staff quota is counted per account: one staff member working in two shops of
  the same owner counts once
- When a paid plan expires, all of that owner's shops become **read-only** until
  renewal. The Free plan never expires

## Getting started

### Prerequisites

- **Node.js 24.x** and **pnpm 11.8.0**. `engine-strict=true` makes the install fail on
  any other Node version
- PostgreSQL
- For the full feature set: Google OAuth client, LINE Login + Messaging API channels,
  Stripe test keys, Cloudinary, Brevo, and an Ollama host

### 1. Clone and install

```bash
git clone https://github.com/wipabhorn-s/aum-manage-stocks.git
cd aum-manage-stocks

cd api && pnpm install     # postinstall also runs `prisma generate`
cd ../web && pnpm install
```

### 2. Configure environment

```bash
cp api/.env.example api/.env
cp web/.env.example web/.env.local
```

Fill in the values. See [Environment variables](#environment-variables).

### 3. Set up the database

```bash
cd api
pnpm prisma db push
```

During development the team syncs the schema with `db push`. `db push` skips
`prisma/sql/`, so `SqlScriptsRunner` applies those scripts when the API starts.
Scripts marked `@manual` are skipped and must be run by hand:

```bash
pnpm prisma db execute --file prisma/sql/<file>.sql
```

Subscription plans are seeded automatically on startup.

### 4. Run both apps

```bash
# terminal 1
cd api && pnpm start:dev        # http://localhost:8000

# terminal 2
cd web && pnpm dev              # http://localhost:3000
```

## Data model

```
User (owner) ──< Shop ──< ShopProduct >── Product ──> Category
                  │            │
                  │            ├──< StockLot
                  │            └──< StockMovement   (append-only ledger)
                  ├──< Sale ──< SaleItem             (snapshot of name / price / cost)
                  ├──< ShopStaff ── StaffPermission >── User (staff)
                  ├──< PendingAction                 (chatbot commands awaiting confirmation)
                  ├──< ChatMessage
                  └──< AiRecommendation
User ──< Subscription >── SubscriptionPlan
User ──< Payment
```

- **Product** belongs to the owner, not to a shop. **ShopProduct** carries the
  per-shop sell price, stock quantity and low-stock threshold. The same product in
  three shops counts once toward the product quota
- **StockMovement** is the source of truth for stock and is never updated or
  deleted. `ShopProduct.stockQty` is a cache, updated in the same transaction as
  each movement
- **SaleItem** stores the product name, price and cost at the time of sale, so old
  receipts never change when prices do
- **Product**, **Shop** and **ShopStaff** use soft delete, so sales and stock history
  are never lost
- Barcodes are unique per owner's catalog, enforced by a partial unique index in
  `prisma/sql/`
- **SubscriptionPlan** carries the feature gates (`chatbot_enabled`,
  `barcode_enabled`, `ai_recommendation_enabled`)

Full definitions: [`api/prisma/schema.prisma`](api/prisma/schema.prisma), the reviewed
design in [`api/prisma/design/schema.dbml`](api/prisma/design/schema.dbml), and a full
ER diagram (every table, column and relationship) in
[`api/prisma/design/erd.drawio`](api/prisma/design/erd.drawio). Open it at
[app.diagrams.net](https://app.diagrams.net) → **File → Open from → Device**. Dashed
lines are links stored as plain UUIDs without a database foreign key.

## Authentication flow

**Password login**

1. The web app posts the credentials to `POST /auth/login` through a Next.js route handler.
2. The API checks the password with bcrypt and returns a short-lived access token
   (15 minutes) and a refresh token (30 days).
3. The web server stores both in **httpOnly cookies**, so browser scripts never see
   them, and attaches the access token to every API call it forwards.

**Two-factor authentication**: when 2FA is on, step 2 returns
`{ requires2fa: true, challengeToken }` instead of tokens. The user enters a TOTP
code (`POST /auth/2fa/verify`) or a recovery code (`POST /auth/2fa/recovery`)
before any token is issued. Google and LINE logins go through the same step.

**Google and LINE**: the web app builds the authorize URL with a random `state`
stored in a cookie, the provider redirects back to the web app, and the API
exchanges the code for the user's identity. The redirect URI is built from the
public origin and must match the one registered with the provider exactly.

**Revoking access**: an access token cannot be revoked, so `AuthGuard` looks the
account up on every request. A deleted account gets `401` and a suspended account
gets `403` immediately, without waiting for the token to expire. The short token
lifetime plus the refresh flow keeps sessions alive for active users.

**Two permission layers**: every action a staff member takes on stock, products,
chatbot, barcode or dashboard has to pass both the per-shop `StaffPermission` the
owner granted **and** the owner's plan feature flags.

**Payments**: the card form uses Stripe's Payment Element on our own page, so card
numbers never reach our servers. `POST /payments/subscription-intent` creates the
PaymentIntent, and `POST /payments/:id/confirm` asks Stripe for the real status
before applying the upgrade. There is no webhook. An hourly job expires unpaid
payments, and a daily job expires subscriptions.

## Deploy

Stack: **Railway** (API + PostgreSQL) + **Vercel** (web app), plus the existing
Cloudinary, Brevo, Stripe (test mode), Google, LINE and Ollama accounts.

> The live demo is currently built from a team member's copy of this repo,
> [`Aum40/aum_manage_stock`](https://github.com/Aum40/aum_manage_stock), which adds
> a few fixes not merged here yet. See
> [`AGENTS.md` → Deployment](AGENTS.md#deployment). The steps below are for
> deploying from this repo.

**1. Database and API (Railway)**
1. Sign up at railway.com with GitHub → **New Project → Deploy from GitHub repo** →
   pick this repo, then **+ New → Database → PostgreSQL** in the same project.
2. In the API service settings:

   | Setting | Value |
   | --- | --- |
   | Root Directory | `api` |
   | Build Command | `pnpm install --frozen-lockfile && pnpm build` |
   | Pre-deploy Command | `pnpm prisma db push` (see the migrations note below before using `migrate deploy`) |
   | Start Command | `pnpm start:prod` |

   `prisma/sql/*.sql` (partial unique indexes, plan seed) runs automatically when the
   app boots, so there is no separate step for it.
3. Add every variable from [`api/.env`](#apienv). Set `DATABASE_URL` to
   `${{Postgres.DATABASE_URL}}`, and `FRONTEND_URL` to the Vercel URL from step 2
   (put a placeholder first). Generate fresh values for `ACCESS_TOKEN_SECRET`,
   `TWO_FACTOR_ENCRYPTION_KEY` and `TWO_FACTOR_CHALLENGE_SECRET`. **Keep
   `TWO_FACTOR_ENCRYPTION_KEY` safe**: losing it locks every 2FA user out.
4. **Settings → Networking → Generate Domain** gives the API URL, e.g.
   `https://aum-manage-stocks-api.up.railway.app`.

**2. Web (Vercel)**
1. **Add New → Project** → import this repo and set **Root Directory** to `web`.
2. Add the variables from [`web/.env.local`](#webenvlocal), with `API_URL` set to the
   Railway URL and `APP_URL` set to the Vercel URL. `NEXT_PUBLIC_*` values are baked in at build time, so redeploy after
   changing them.
3. Deploy, then put the production URL into `FRONTEND_URL` on Railway. CORS and the
   OAuth redirect URIs are built from it, so it must match exactly (no trailing slash).

**3. Callbacks**
- **Google Cloud Console** → OAuth client: add the web URL to *Authorized JavaScript
  origins* and `<web URL>/api/auth/google/callback` to *Authorized redirect URIs*.
- **LINE Login channel** → Callback URL: `<web URL>/api/auth/line/callback`. Linking an
  account from the profile page uses the same two callbacks.
- **LINE Messaging API channel** → Webhook URL: `<API URL>/webhooks/line`, then turn
  **Use webhook** on.
- **Stripe** needs no webhook. The web app confirms each payment through
  `POST /payments/:id/confirm`, which checks the PaymentIntent with Stripe on the server.

**4. Check**: register, verify the email, create a shop and a product, then buy a
plan with a Stripe test card.

**Migrations:** `prisma/migrations/` holds the old history (`202608*`) and the
rebuilt set the Railway database was built with (`20260902000000_baseline` onward).
Both create the same tables, so `prisma migrate deploy` fails while both are there.
Use `db push` until the team decides what to do with the old set.

`api/scripts/seed-test-users.sql` creates one test account per role (including a
super admin) with a password written in the file. Use it on local or staging
databases only, never on one real users can reach.

## Team

A five-person team project. Work was split by module, one feature branch each:

| Member | Modules |
| --- | --- |
| แพรว | Auth, Users, Admin, Payments |
| พี่ปาน | Subscriptions, Shops |
| อั้ม | Staff, Categories |
| เซิ่น | Products, Shop products |
| พี่ดิว | Stock movements, Sales |

Later modules, by the same split: chatbot, LINE and AI recommendations (อั้ม),
notifications and lot-based cost (เซิ่น), stock adjust / transfer (พี่ดิว).
Team rules (git workflow, ownership, business rules) live in [`AGENTS.md`](AGENTS.md).
